# 阶段 0：通信协议设计

> 本文是**规格说明书**，不含实现代码。
> 后续 `computer/net/protocol.py`（编解码）与 `server.py`（连接与调度循环）严格按本文实现；`phone/NetClient.kt` 同理。
> 上游约定：同一 WiFi、手机手填电脑 IP、TCP、6 位配对码，详见 [PLAD.md](../../PLAD.md) 第六节。

---

## 1. 设计约束

| 约束 | 来源 | 对协议的影响 |
| --- | --- | --- |
| 1 台手机 : 1 台电脑 | P6 | 不需要设备路由表，一个连接就是全部 |
| 电脑主控 | D5 | 决策只在电脑算，手机是"上报 + 执行" |
| 手填 IP | D9 | 无设备发现消息，`hello` 是第一条报文 |
| 配对码 | D9 | 未通过校验的连接不允许发任何业务消息 |
| 不做降级 | P5 | 断线不需要"恢复"类消息，直接结束 |
| 网络课可讲解 | PLAD 第二节 | 报文保留长度前缀、心跳、超时等可观测细节 |

**一句话**：协议只解决三件事——谁在播（状态）、该谁播（决策）、现在暂停（命令）。

---

## 2. 传输层

- **模型**：电脑是 TCP 服务端（`0.0.0.0:8765`），手机是客户端主动连接。
- **为什么不用 UDP**：控制消息量极小（每秒最多几条），但要求必达、有序、不丢。TCP 直接满足；UDP 要自己做重传与排序，白费力气。
- **为什么不用 WebSocket**：多一层 HTTP 握手，报文反而看不清，不利于答辩讲解。
- **单连接**：同一时刻只允许一个手机连接。第二个连接到达时，服务端回 `hello_reject{code:"BUSY"}` 后立即关闭。

**连接生命周期**（状态只增不退，方便排查）

```
CONNECTING ──TCP 建立──> AUTH ──hello_ok──> READY ──超时/异常──> CLOSED
                            └──hello_reject──> CLOSED
```

## 3. 应用层帧格式

```
┌──────────────┬───────────────────────────────┐
│ 4 字节长度 N  │  N 字节 UTF-8 JSON 正文        │   ← 重复
└──────────────┴───────────────────────────────┘
```

| 规则 | 值 | 说明 |
| --- | --- | --- |
| 长度字段 | 无符号 32 位**大端** | 只表示正文长度，不含自身 4 字节 |
| 正文编码 | UTF-8 | 中文 app 名也不乱码 |
| 正文顶层 | JSON **对象** | 不允许是数组或裸字符串 |
| 最大长度 | 65535 字节 | 超过即视为畸形包，直接断开 |
| 保活 | TCP 自身 + 应用层 ping | 见第 6 节 |

**为什么必须带长度**：TCP 是字节流，两次 `send` 可能被合成一次收到，一次 `send` 也可能分几次收到（粘包 / 拆包）。只有先读 4 字节拿到长度，才知道正文该读多少。

**示例**（`{"type":"ping","ts":1}` 共 23 字节）

```
00 00 00 17  7B 22 74 79 70 65 22 ... 7D
```

## 4. 消息总表

| 编号 | 方向 | `type` | 触发时机 | 频率 |
| --- | --- | --- | --- | --- |
| M1 | 手机→电脑 | `hello` | TCP 连上后的第一条 | 每次连接 1 次 |
| M2 | 电脑→手机 | `hello_ok` | 配对码与版本校验通过 | 每次连接 1 次 |
| M3 | 电脑→手机 | `hello_reject` | 配对码错 / 协议版本不符 / 已有连接 | 随即断开 |
| M4 | 手机→电脑 | `phone_state` | 播放状态变化时立即 + 每 1 秒兜底 | ≤ 5 条/秒（限速） |
| M5 | 电脑→手机 | `decision` | `mode` 发生变化时 | 变化才发 |
| M6 | 电脑→手机 | `pause_cmd` | 决策为 `pc` 且手机仍在播 | 每次决策变化最多 1 条 |
| M7 | 手机→电脑 | `pause_ack` | 执行 `pause_cmd` 后（含回读结果） | 每条命令 1 条 |
| M8 | 双向 | `ping` / `pong` | 定时 | 每 3 秒 |
| M9 | 双向 | `error` | 收到无法解析 / 越权报文 | 异常时 |

**公共字段**（所有消息都带）

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `type` | string | 是 | 消息类型，见上表 |
| `v` | int | 是 | 协议版本，首版固定 `1`；不一致直接 `hello_reject` |
| `ts` | int | 是 | 发送方本地时间，Unix 毫秒。仅用于日志对齐，**不用于决策** |

## 5. 逐条字段定义

### M1 `hello`（手机→电脑）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `device_id` | string | 手机首次启动生成并持久化的 UUID，用于日志区分 |
| `device_name` | string | 手机型号，仅显示用 |
| `pair_code` | string | 用户输入的 6 位数字 |
| `app_ver` | string | 手机 app 版本号 |

```json
{"type":"hello","v":1,"ts":1731111111123,"device_id":"a1b2...","device_name":"Pixel 7","pair_code":"123456","app_ver":"1.0"}
```

### M2 `hello_ok`（电脑→手机）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `session_id` | string | 本次连接的编号，日志用 |
| `server_name` | string | 电脑名，手机状态页显示 |
| `heartbeat_s` | int | 心跳周期，首版固定 `3`，由服务端下发便于以后调整 |

### M3 `hello_reject`（电脑→手机）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | string | `BAD_PAIR_CODE` / `BAD_VERSION` / `BUSY` |
| `msg` | string | 给用户看的中文原因 |

### M4 `phone_state`（手机→电脑）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `seq` | int | 自增序号，从 1 开始，用于发现丢包与乱序 |
| `playing` | bool | 是否有"正在播放"的合规 app |
| `package` | string | 正在播放的包名；`playing=false` 时为空串 |
| `app_name` | string | app 显示名，仅日志/界面用 |
| `state_code` | int | 直接透传 Android `PlaybackState` 常量：`0` NONE、`1` STOPPED、`2` PAUSED、`3` PLAYING、`6` BUFFERING、`7` ERROR |
| `has_control` | bool | 该 app 是否能下发暂停（拿得到 `TransportControls`） |

**上报规则**（防抖）

1. 每 1 秒轮询一次 MediaSession，**状态与上次不同则立即发**。
2. 即使没变化，也每 1 秒发一次兜底（电脑端据此判断"手机还在，只是没在播"）。
3. 限速：200ms 内最多 1 条，避免某些 app 频繁抖动刷屏。
4. `playing` 为真的判定：`state_code == 3` 连续 2 次读到（约 2 秒），避免一秒内的提示音误触发。

### M5 `decision`（电脑→手机）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `mode` | string | `pc` / `phone` / `none`（两边都没在播） |
| `reason` | string | 见下表，便于日志排查 |
| `pc_app` | string | 电脑侧当前参与比较的进程名（无则空串） |
| `phone_app` | string | 手机侧当前包名（无则空串） |
| `pc_priority` | int | 电脑侧优先级 |
| `phone_priority` | int | 手机侧优先级 |

| `reason` 取值 | 含义 |
| --- | --- |
| `ONLY_PC` / `ONLY_PHONE` | 只有一侧在播 |
| `PC_HIGHER` / `PHONE_HIGHER` | 两侧优先级不同，高者胜 |
| `TIE_KEEP_CURRENT` | 优先级相同，维持当前正在播的一方（P2） |
| `NONE` | 两侧都未在播 |

只在 `mode` 变化时发送，避免每秒刷屏；手机状态页据此显示"当前由谁播"。

### M6 `pause_cmd`（电脑→手机）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `cmd_id` | int | 电脑侧自增，用于与 `pause_ack` 配对 |
| `package` | string | 要暂停的包名 |
| `reason` | string | 固定 `PC_WINS`，留给以后扩展 |

### M7 `pause_ack`（手机→电脑）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `cmd_id` | int | 原样回传 |
| `ok` | bool | 执行并**回读**后是否确实已不在播放 |
| `state_code` | int | 回读到的 `PlaybackState` 常量 |
| `err` | string | 失败原因，成功时为空串（如 `NO_CONTROL` / `STILL_PLAYING` / `APP_GONE`） |

**为什么必须回读**：`pause()` 是"请求"不是"保证"，个别 app 会忽略或自动续播。回读后 `ok=false` 要写进电脑日志，不能假装成功。

### M8 `ping` / `pong`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `ts` | int | 发送时间，`pong` 原样回传，可用于估算 RTT |

### M9 `error`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | string | `BAD_FRAME` / `UNKNOWN_TYPE` / `NOT_AUTHED` / `TOO_LARGE` |
| `msg` | string | 描述 |

> 收到 `error` 不重连、不重试；`BAD_FRAME` / `TOO_LARGE` 之后直接断开（对端已经不可信）。

## 6. 时序

### 6.1 建连与配对

```
手机                                     电脑
 │  TCP connect ───────────────────────>  │  绑定 0.0.0.0:8765
 │  hello{device_id, pair_code} ───────>  │  校验 pair_code / v
 │  <────────────────── hello_ok{session_id, heartbeat_s}   进入 READY
 │  <────────────────── hello_reject{code}                   立即关闭
```

- 配对码错：**不重试、不提示"再试一次"之外的任何信息**，手机端显示原因由用户重新输入。
- 未通过 AUTH 前收到任何非 `hello` 报文 → 回 `error{NOT_AUTHED}` 并断开。

### 6.2 一次完整切换（手机在播 → 电脑抢播）

```
手机                                  电脑
 │ phone_state{PLAYING, 网易云} ────>  │ 枚举 WASAPI：Chrome 在播
 │                                    │ 优先级：手机 20 > 电脑 5
 │ <────────────── decision{phone}     │ 静音 + 让电脑侧会话停止出声
 │ ping ───────────────────────────>  │
 │ <──────────────────────────── pong  │
 │                                    │ 用户在电脑点开网易云（优先级 10）
 │                                    │ 此时电脑侧最高 10 < 手机 20
 │                                    │ 仍保持 phone，不发新 decision
```

### 6.3 电脑胜出并下发暂停

```
 │ <────────────── decision{pc, PC_HIGHER}
 │ <────────────── pause_cmd{cmd_id:7, package:"com.netease.cloudmusic"}
 │ 调用 transportControls.pause()
 │ 回读 PlaybackState
 │ pause_ack{cmd_id:7, ok:true, state_code:2} ────────>
```

### 6.4 超时与断线

```
心跳：每 3 秒双向 ping；连续 6 秒（2 个周期）没收到对端任意报文 → 判离线
```

| 事件 | 电脑侧动作 | 手机侧动作 |
| --- | --- | --- |
| 判离线 | 关闭 socket、停止调度；**不主动改动当前静音状态**（P5）；日志记录 | 显示"未连接"，退回独立播放 |
| 程序正常退出（Ctrl+C / 关窗口） | 恢复自己改过的所有静音（D2） | — |
| 手机重启服务 | 退避重连：1s → 2s → 4s → 8s → 10s（上限 10s） | 同左 |
| `pause_cmd` 2 秒内无 `pause_ack` | 记一条超时日志，**不重发**；等下一次 `decision` 变化再触发 | 无 |

## 7. 幂等与顺序

| 场景 | 处理 |
| --- | --- |
| `decision` 重复收到 | 幂等，直接覆盖本地显示 |
| `pause_cmd` 重复 `cmd_id` | 手机端按 `cmd_id` 去重，只执行一次，仍回 `pause_ack` |
| `phone_state` 乱序 | 按 `seq` 丢弃比已处理序号小的包 |
| 报文长度不足 4 字节 | 继续等，不报错 |
| 长度 > 65535 | 回 `error{TOO_LARGE}` 并断开 |

**关键原则**：`decision` 是"状态"，`pause_cmd` 是"命令"。状态可以随便重发；命令必须去重。

## 9. 边界与坑

1. **app 名统一小写比较**：Windows 进程名大小写不稳定（`NeteaseCloudMusic.exe` / `neteasecloudmusic.exe`），比较前统一 `lower()`。
2. **手机侧包名、电脑侧进程名不是一回事**，配置里用 `device` 字段区分，不能跨设备比较名字。
3. **`playing=false` 也要发**：否则电脑无法区分"手机没在播"和"手机掉线了"。
4. **不要用 `ts` 做决策**：两端时钟不同步，`ts` 只用于日志。
5. **一个 app 可能有多个 MediaSession**：取 `state_code == PLAYING` 的那个；都暂停时取最近活动的。
6. **中文**：`app_name` 直接放 UTF-8，配合长度前缀不会有乱码问题。
7. **防火墙**：首次运行要允许 `python.exe` 入站（专用网络），否则手机连不上，表现与 AP 隔离相同。
